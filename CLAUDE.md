# XPLPC

Cross Platform Lite Procedure Call. A C++ core lets any supported language call a procedure implemented in any other supported language, transporting serialized data through device memory instead of a network protocol.

## Architecture

A call always follows the same path, regardless of which side starts it:

```
caller  ->  Client  ->  PlatformProxyList  ->  PlatformProxy  ->  target function
                              |                                         |
                          CallbackList  <----  serialized response  <----
```

- **Request** carries a function name plus named parameters. C++, Kotlin and Swift serialize at construction, so the request is fixed once it exists and building one before `initialize` fails there. Dart, Python and TypeScript serialize inside `data()` instead, which is what lets those three build a request before the library is up, and is why only they can test being reached uninitialized without the request itself raising first.
- **Client** registers a callback under a generated unique key, then asks every registered proxy, in order, which one owns the function name. The first proxy that answers `hasMapping` receives the call. When nothing owns it, the registration is dropped and the caller is answered with an empty value.
- **PlatformProxy** is the bridge to one language. `NativePlatformProxy` resolves C++ mappings, `CNativePlatformProxy` forwards to C function pointers, `JNIPlatformProxy` to Kotlin, `ObjCPlatformProxy` to Swift, and the WASM binding to JavaScript.
- **MappingList** maps a function name to a `MappingItem`, holding the target function and a type erased executor that knows how to decode the parameters and encode the return value.
- **CallbackList** holds pending callbacks keyed by unique id. A key is always taken, never read then removed, so a response can only ever resolve once.
- **Serializer** is JSON only today, selected by the `XPLPC_SERIALIZER_JSON` compile definition. The wire format is `{"f": <function name>, "p": [{"n": <name>, "v": <value>}]}` for requests and `{"r": <value>}` for responses.

An incoming request is read once. A proxy used to ask the serializer for the function name and then for the parameters, which parsed the same document twice on every call, so `decodeRequest` answers with both and the five host bridges carry it as a `DecodedRequest` holding the name and the message.

C++ is the one that has no such type, and the reason is that it decodes a parameter against the type the mapping signature declares rather than reading whatever the wire carried. The message cannot be filled before the mapping is known, so there is nothing for a `DecodedRequest` to hold at the moment the other bridges build theirs. It reads the document once all the same: `decodeFunctionName` is a sax scan that stops at the `f` field and never builds the document for routing, and the executor a `MappingItem` holds receives the name the proxy already resolved rather than reading it again. That took a full C++ round trip from 7001 to 5172 nanoseconds, measured as the minimum of nine runs, since a single sample of either moves by about a fifth on its own. What none of this touches is how a value is decoded, since a return value is still filled by whatever each language uses to build an arbitrary consumer class, so a type nobody declared crosses exactly as it did before.

Every language reimplements `Client`, `CallbackList`, `MappingList`, `Serializer`, `Message`, `Param`, `Request`, `DataView` and `UniqueID` with the same responsibilities and the same file layout. When changing one of them, check whether the other languages need the same change.

`Response` is the other exception, and there it is the shape of a mapping that differs rather than the file being absent. C++, Kotlin, Swift, Dart and Python hand a mapping something to answer through, so a mapping there takes a message and a responder and returns nothing. TypeScript hands it nothing and reads what it returns, since a mapping that answers with a promise is what a caller there already knows how to wait on, so there is no `Response` to name.

A key has to be unique among the entries pending at one moment, not for the life of the process, because `CallbackList` takes the key when it answers and frees it for reuse. A monotonic counter satisfies that with no ceiling worth reaching: repeating a key would need the counter to wrap all the way round between two calls that are both still waiting, and the number of waiting calls is bounded by the memory each one holds. That is why a counter is right here and why an unbounded id, a uuid or an address would each cost more and prove nothing extra. A key crosses the bridge twice on every call, out with the request and back with the answer, so a uuid would add about fifty bytes per call to a transport whose whole reason to exist is moving bytes through memory, and it would buy a guarantee the counter already has. What the counter does have to be is defined at the end rather than silent, which is the paragraph below.

The counter is the one piece of shared state every call touches before anything else, and nothing generated a key from more than one thread at a time. C++, Kotlin and Python hammer it directly now and assert every key came out distinct. Swift keeps `UniqueID` internal and the suite imports the framework plainly, so reaching it would mean widening the public surface for a test, and there it is covered by consequence instead: a repeated key would overwrite a pending entry, and `testClientAnswersEveryCallFromEveryThread` asserts every one of its calls was answered and that nothing is left registered.

What matters is that reaching the end is defined rather than fatal. C++ uses an atomic `uint64_t`, Kotlin an `AtomicLong` and Dart an int, all of which wrap by definition, and Python counts with an unbounded integer. Swift was the one that would end the process instead, since its arithmetic traps on overflow, which a compiled program proves by exiting on a signal. It wraps explicitly now. TypeScript was the exception twice over and is why the ceiling is worth stating rather than waving at. A number there is a double, so `++` stops changing it past `Number.MAX_SAFE_INTEGER` and every key from then on is the same one, which is not a wrap at all: a wrap only collides if the lapped key is still pending, while a counter that stands still collides with the call before it every single time. Measured, it repeats `9007199254740992` for good. It counts with a `BigInt` now, which has no ceiling, and the key was already being stringified so nothing else changed.

Unique keys are prefixed per language (`CXX-`, `KT-`, `SW-`, `FL-`, `PY-`, `JS-`) and every one of them counts from one. Each `CallbackList` is written only by the client of its own language, so the prefix is not what keeps them apart and is there to say where a key came from when one shows up in a log. The C layer generates none of its own, it carries the key the host handed it.

`DataView` carries a raw pointer plus a size, letting large buffers cross the bridge without being copied or base64 encoded. The pointed memory must stay valid and immovable for the whole call, which each language guarantees differently:

| Language | Ownership |
| --- | --- |
| C++ | The caller owns the buffer, `DataView` only borrows it |
| Swift | `DataView.withByteArray` scopes the address to its closure, the view must not escape it |
| Kotlin | `createFromByteBuffer` borrows a direct buffer, `createFromByteArray` copies into a direct buffer the view keeps alive |
| Dart | `createFromByteBuffer` borrows native memory the caller owns, `allocateFromByteArray` owns what it allocated and releases it with `dispose` |
| TypeScript | `DataView` owns the heap memory it copied, released by `DataView.free`, which ignores a view it did not allocate, and the bytes are read through `DataView.withUint8Array` |
| Python | `create_from_byte_buffer` keeps the exported buffer inside the view, so the source cannot move or be released while it lives |

A managed heap may move an object, so no language ever takes the address of a garbage collected array. Off heap storage or an explicit copy is used instead.

A view decoded from a response can carry no address at all, so every helper that reads one answers with nothing rather than reading from it. The jni helper faulted on address zero, the dart one took the isolate down with it, and neither is something a sanitizer sees because the read is a perfectly valid instruction on an address the process never owned.

Two rules follow from this and are easy to break without any test noticing. A mapping that answers with a view must keep the buffer alive after it returns, because the bridges read it once the call has unwound, so a local is not enough. And a view is released only by the side that allocated it, so a caller never frees a view a mapping handed it.

## Wire format

The C++ core defines the format and every bridge has to agree with it byte for byte. A serializer that encodes the same value differently produces a request the other side silently misreads, which no round trip test on a single platform can catch, so each platform pins the format in its own test. Those tests each assert against a literal written by hand in their own language, which is why comparing one bridge's output against another's found what none of them could: python spaced its output where the other five write it compact, and the bytes are what the claim above is about. Key order is the one thing that is not part of it, because `JSONEncoder` serialises a dictionary rather than the order a `Codable` wrote its keys in, so swift emits `{"v":1,"n":"a"}` where the other five emit `{"n":"a","v":1}` and no reader can tell, json objects being unordered. Five bridges pin the exact bytes and swift pins the length and the absence of a space, which is what it can promise.

| Value | On the wire | Notes |
| --- | --- | --- |
| Whitespace | None | The document carries no space a parser would ignore, since the bridge pays for every byte it copies |
| Character | Integer code point | Swift uses `CodePoint`, not `Character`, because a grapheme cluster has no single code point |
| Date | Integer milliseconds since the unix epoch | Carried as a type by C++, Kotlin and Swift only |
| DataView | `{"ptr": <address>, "size": <bytes>}` | |
| Null | `null` | A parameter without a value keeps its name, and a mapping with nothing to answer travels the same way |
| No parameters | `"p": []` | An empty array, never null and never absent, and a reader treats all three as no parameters |
| Infinity and not a number | Nothing | Json has no token for either, so a value that is not finite never reaches the wire |

Dart, Python and TypeScript carry neither a character nor a date type, so a caller there sends the code point or the milliseconds itself and the serializer reports anything else rather than writing it wrong. Those three pinned the conversion anyway, by handing the serializer an integer and asserting the same integer came back, which is what the integer test already proves and cannot fail for any other reason. What they pin now is the failing path they actually have.

Two limits come from the languages themselves. Swift's `JSONEncoder` writes dates as seconds since the Apple reference date by default, which is why the serializer installs its own strategy.

The other is JavaScript. A number there is a double, so an integer literal above `Number.MAX_SAFE_INTEGER` is rounded on parse. The format itself is fine and every other platform reads such a value exactly, so the fix belongs on the JavaScript side and not on the wire: quoting large integers would need the sender to know the value is a 64 bit integer, which Dart, Python and TypeScript cannot know because nothing on the wire carries the declared type. The TypeScript serializer therefore inspects the original text through the parse reviver and rejects a value it would have to round, turning silent corruption into a reported failure. Reading that text is an ES2025 addition to `JSON.parse` and the sample builds for `esnext` without transpiling, so on a runtime that does not provide it the check has nothing to compare against and the rounding goes back to being silent. The suite pins both, the rejection and what the plain parser does without it. Code that genuinely needs the full 64 bit range across the wasm bridge should declare that field as a string in its own mapping, which every platform already carries exactly.

## Tooling

Every task runs through `python3 xplpc.py <task>`. Run `python3 xplpc.py -h` for the full list. The common ones:

```
python3 xplpc.py cxx-test
python3 xplpc.py c-test
python3 xplpc.py swift-test
python3 xplpc.py swift-test --platform ios
python3 xplpc.py swift-test --platform ios-device
python3 xplpc.py kotlin-test --platform desktop
python3 xplpc.py flutter-test
python3 xplpc.py python-test
python3 xplpc.py <language>-format
```

The Flutter and Python suites need the native library first:

```
python3 xplpc.py swift-build --interface --platform macos-flutter
python3 xplpc.py swift-build-xcframework --platform macos-flutter
python3 xplpc.py c-build-shared && python3 xplpc.py python-install
```

`kotlin-test` does not build the native library, so a change under `cxx`, `c` or `jni` is only picked up after `kotlin-build --platform desktop`. Running the suite without it tests the previous binary and passes for the wrong reason. `wasm-test` behaves the same way against `wasm-build`.

Kotlin runs one suite on two runtimes. `kotlin/shared/tests` is compiled by the desktop project against the jvm and by the android project against a device, the same way `kotlin/shared/src` is, so a test cannot exist on one and not the other. It was two hand kept copies before, and every kind of drift that allows did happen: four unguarded tests were corrected on desktop and left alone on android, and the data view, serializer and stress suites were missing there entirely, on the runtime that is the only one running r8, a real garbage collector and the jni byte buffer helpers against a moving heap.

Two things stay per project because they genuinely differ. `TestPlatform` brings xplpc up, which desktop has to ask for and android already got from the content provider that is its platform initializer. And `ContextTest` checks the application context, which means nothing off a device. Anything else belongs in the shared set.

The iOS sample project is generated, not hand edited, and building it regenerates it first so the committed project cannot drift from the spec:

```
python3 xplpc.py swift-generate-sample-project
python3 xplpc.py swift-build-sample
```

A swift package manager consumer reaches the library as a binary target, which is one archive and one checksum, so the slices cannot be split the way the other swift tasks split them:

```
python3 xplpc.py swift-build --platform apple
python3 xplpc.py swift-build-xcframework --platform apple
python3 xplpc.py swift-generate-spm-package
```

The `apple` platform exists only for this and carries ios, tvos, watchos, mac catalyst and macos at once, since building `ios` and `macos` separately leaves two xcframeworks and a package can name neither. The archive is written with `ditto` rather than `zip`, because a macos framework is a bundle built out of symlinks and flattening them into copies produces an archive that no longer loads. The checksum ties the package to those exact bytes, so the archive is published to the url the package names and republishing anything means regenerating both. Neither one is committed, since the package is written beside the archive under `build/swift-apple-xcframework` and reaches a consumer from wherever that pair is published. The declared platforms are read from the same target definitions the build uses rather than written by hand, which is what keeps a raised deployment target from being remembered in two places. The package itself comes from `swift/spm/Package.swift.in`, which is the file to edit when the manifest has to change, since a template read from disk is reviewable as swift where a string built inside the task runner is not. Only the platform list, the url and the checksum are substituted into it, and the generation stops rather than inventing a manifest when the template is missing. The url is read from the version the build declares and points at the release named after it, which is the shape a published archive takes, so `--url` is only needed to publish somewhere else.

The samples are the only consumers of the public surface, so a changed entry point breaks them silently and CI builds every one it can. Two cannot be built that way and are covered differently. The flutter example is analyzed inside `flutter-test`, which resolves every name it calls without needing a device. The python sample is a KivyMD application that no headless runner can start at all, so the python public surface is held by the suite instead, which drives `call`, `call_from_string`, `call_async` and `call_async_from_string` directly. The sample also carries the suite to the simulator: an XCTest bundle needs a host application to run there, and the sample is one, so `swift-test --platform ios` runs the same tests against the shipped xcframework rather than against the sources. That is why the suite imports `xplpc` plainly instead of testably, and why nothing it touches is internal. The runner decides which simulators exist, so the first available iPhone is used rather than a fixed model. A connected iphone runs the same suite through `swift-test --platform ios-device`, which signs the sample rather than skipping it and picks the first device that is online. No hosted runner has one, so that task is local only and the simulator is what ci reads.

The C++ and C suites also build under instrumentation, which is where a race or a memory defect actually shows up:

```
python3 xplpc.py cxx-test --sanitizer thread
python3 xplpc.py cxx-test --sanitizer address
python3 xplpc.py cxx-test --sanitizer undefined
python3 xplpc.py swift-test --sanitizer undefined
python3 xplpc.py swift-build --interface --platform ios-simulator --sanitizer thread
python3 xplpc.py swift-build-xcframework --platform ios-simulator
python3 xplpc.py swift-test --platform ios --sanitizer thread
```

`thread` finds unsynchronized access between threads, `address` finds use after free and out of bounds, and `undefined` finds signed overflow, misaligned access and invalid casts. A sanitizer only reports what the run actually reaches, so the stress suites exist to make the registries collide on purpose.

Which tool can reach which bridge is not obvious and was established by running each one rather than by reasoning about it:

| Bridge | address | undefined | thread | How |
| --- | --- | --- | --- | --- |
| C++ core | yes | yes | yes | its own suite |
| C abi | yes | yes | yes | its own suite, and again with the python suite driving an instrumented shared library |
| JNI | partly | yes | **no** | the library is built with the sanitizer and the kotlin suite runs against it, except the thread one, which refuses to work through a preload into a jvm and dies before gradle starts, while the address one aborts on the first c++ exception thrown and so covers only the paths that do not raise |
| Objective-C | yes | yes | yes | undefined on macos, thread and address on the simulator |
| Dart | yes | yes | **no** | the flutter suite on linux against an instrumented shared library, except the thread one, which segfaults the dart vm through a preload the same way it does a jvm |
| WASM | yes | yes | n/a | emscripten builds the module with the sanitizer, and the module is single threaded |
| Python | yes | yes | yes | the suite against an instrumented shared library, plus a run on a free threaded interpreter |

A run only means something if the instrumentation was actually there, so each of those jobs fails before its first test unless it finds the runtime linked, and the plain build is checked to be plain so it cannot pass as an instrumented one. Each of those runs is a job in the workflow of the language it belongs to, since a table describing coverage is worth nothing unless something runs it on every push.

The two platforms find a leak differently. Linux gets it from the address sanitizer, which turns its leak detector on by itself and needs nothing set. macOS has no leak detector in that sanitizer at all, so `cxx-build-leaks` and `c-build-leaks` run a debug build under Apple's own `leaks` with `MallocStackLogging` set, and those tasks only exist for that platform since the tool is `/usr/bin/leaks`. Both jobs report a leak, by different means, and neither covers the other.

The Swift suite reaches a sanitizer two ways, one per runner. On macOS the tests are an XCTest bundle opened with `dlopen`, and address and thread both need their runtime in the process before it starts, which a bundle loaded later cannot give them, so only undefined runs there and asking for either of the other two says so rather than aborting mid run. On the simulator xcodebuild launches the host application and can instrument it, so thread runs there, but only against a framework built from the simulator slices alone, since `-fsanitize=thread` is an unsupported option for a device triple. That is the only cover the objective-c bridge has for a race, and the stress suite is what covers the Swift locking on top of it, failing on a lost callback, a wrong count or a lock that is never released.

Dependencies come from CPM by default, or Conan with `--dependency-tool conan`, which is also what `dependency_tool` in `core/config.py` sets for every task at once. Both resolve the same versions, declared in `cmake/cpm/cpm-dependency.cmake` and `conanfile.py`, and must be kept in sync.

That obligation had no guard and the conan path had no consumer: the default never changed, no workflow changed it, and the `conan-setup` step every job runs only writes a profile. So the whole conan branch, its recipe and its nine profiles were maintained and never built, which is the shape the flutter android target rotted in. The c++ and c suites run through it on the linux, macos and both windows jobs now, since a version that drifts apart from the cpm one is the failure this is for, and three os families is what makes a recipe that only resolves on one of them show. The other six were recorded as building nowhere for want of a cross toolchain, and all six resolve and build their dependencies on a mac, since conan carries the ndk and the emsdk as tool requirements and the apple sdks come from xcode. What no job does is run them, because that is fmt and spdlog compiled from source five more times on every push to prove a conan center recipe still works, so the measurement is written here rather than turned into a step. What a profile names for arch, `os.version` and `os.sdk` is a default the task always overrides from the same target definitions the build uses, so reading a profile tells you nothing about what a slice is actually built with, and the deployment target is not remembered twice.

The Conan path targets Conan 2, and the apple settings a darwin recipe used to carry are configuration entries the tasks pass directly. Three of its rules differ from Conan 1 and are easy to get wrong: the profile is created with `conan profile detect`, the Apple toolchain switches are configuration entries passed with `-c:h tools.apple:*` rather than recipe options, and `conan install` writes its generators next to the recipe unless `--output-folder` is given, which would otherwise scatter `conan_toolchain.cmake` over the repository root. The embedded Apple platforms carry an `os.sdk` setting the task passes per slice, and macOS proper carries none. Mac catalyst carries none either, since conan 2 gives `Macos` a `version`, an `sdk_version` and a `subsystem` and no `sdk` at all, and what it does need is `os.subsystem.ios_version`, which the task passes from the same slice definition the deployment target comes from.

## Testing

Every suite drives the same round trip, and a green run proves nothing unless it proves the callback ran. Assertions written inside a `Client.call` callback are the natural shape for these tests and also the natural way to write one that can never fail, because the callback is invoked from a frame the test does not control.

Each bridge loses a failing assertion differently. JNI has to clear a pending Java exception before it can make another JNI call, so whatever a Kotlin callback throws is reported and dropped. A Dart callback made with `Pointer.fromFunction` cannot let an exception cross the native frame that invoked it, so a failed expectation is printed and the suite still reports success. A TypeScript test that creates a promise without handing it back finishes before the assertions inside it ever run. C++ and Swift do record a failure, but only if the callback runs at all, and a mapping that answers later means it does not.

So each suite verifies invocation and not only the value:

| Bridge | Guard |
| --- | --- |
| C++ | `VerifiedCall::run` for an inline answer, `AnswerWaiter` when the mapping answers later |
| C | `ProxyCallbackRecorder::waitForAnswerFromThread` |
| Swift | `verifyCall`, built on `XCTestExpectation` |
| Kotlin | `verifyCall`, which captures what the callback threw and raises it after the call |
| Dart | `verifyCall` and `verifyCallFromString`, the same shape |
| TypeScript | the test returns the promise, so the runner waits for it |
| Python | assertions sit on the value `Client.call` returns, so nothing is hidden |

A guard is worth only what it was proven to be worth. Break one assertion on purpose and watch the suite go red before trusting it. Every guard above was checked that way, and the Kotlin, Dart and TypeScript ones were sitting on tests that could not fail at all.

The guard belongs on every suite that reads a response, not only the one named after the client. Guarding the client suite alone left the object suites still unable to fail, which showed up the moment the values they send were changed and nothing complained. A suite that checks a value it never proved arrived is the same defect wherever it lives. Having the guard in a file is not the same as using it, either: the kotlin object suites declared `verifyCall` at the top and then called `Client.call` directly in the four tests that send a list, so those four could not fail while the tests above them could.

One path was checked by a single suite for a long time. Calling a name nothing owns is the only one where no proxy is involved at all, since the client has to drop the registration it just made and answer the caller itself, and a leak there stays invisible until a long lived process runs out. Only the c++ suite went near it. Every suite now asserts both the empty answer and the registration count coming back to what it was.

The values a type test carries decide what it proves. A round trip of `1` and `2.2` exercises the plumbing and nothing else, so each one sends the edges instead: the smallest signed value of every width, an integer past what a double can hold exactly, and a fraction no binary float represents. Every bridge sends them, which took a while to be true: dart, python and typescript carried only `sample.todo.single` with an id of `1` and a title of `Title 1`, so three of the six never put an edge on the wire at all. The wasm bridge is the one exception on the integer, and only because a javascript number cannot hold `9007199254740993` even as a literal, so it sends `Number.MAX_SAFE_INTEGER` and the serializer test pins what happens to anything larger.

Decoding a list of objects into a typed list is not something every bridge does. C++, Kotlin and Swift answer with real instances, and their tests read fields off them. Python answers null, deliberately, because a list cannot fill an object and filling one element at a time would be guessing at a type the wire never carried. Dart answers the decoded maps, and TypeScript erases the parameter, so neither is holding instances whatever the call site declares. Only the shape a bridge actually returns is worth asserting on, which is why the three of them read the maps.

A stress suite clears its registries before each test as well as after. Clearing only afterwards makes a test read what the previous one left, and the result then depends on an order nothing guarantees.

A call has three shapes and each one has to be checked separately, because a bridge can carry one and lose another. The first is a caller reaching a mapping the core owns. The second is the core reaching back for a mapping the caller owns, which `sample.reverse` sets off by calling `platform.reverse.response`, and the value that mapping produces has to travel out through the call that started it. The third is the native side invoking a host mapping directly, which is what `platform.battery.level` is for.

Every bridge covers all three now. The c++ suite covered the second only in the shape where nothing owns the inner name, answering `response-is-empty`, while the other five registered the mapping and asserted `response-is-ok`, so the reference implementation was the one never checking that a nested answer comes back at all. The c suite reaches the same three through the abi rather than through those names, since the host there is whatever linked it, and `from-host` is the value it proves came back.

The nested shape has a late variant of its own, and it is the one a real host hits first. `sample.reverse` is a C++ mapping that calls a host mapping and builds its answer from that one, and every suite answered the inner call inline, so nothing proved the outer answer survives an inner one that arrives later. Every bridge covers it now, since that is what a host doing a network request inside a nested call actually does. It works because `callbackReverse` captures the responder by value, which is the rule every mapping that outlives its frame has to follow.

The c suite reaches the nested shape through the abi too now, both with the host answering the inner call at once and with it taking its time, since that is the composition dart and python actually run and the only place it meets a sanitizer.

The channel that carries a call *into* the host from a foreign thread had no test at all, only the one carrying an answer did. Dart and Python register both in production, and nothing exercised the first, so the c suite now calls a host owned name from a thread it started and asserts the host received it through the owned buffers and answered.

Two shapes are not expressible everywhere and their absence is not a gap. A call made from a thread the bridge does not own means nothing on dart or javascript, where an isolate and a page each run on one. A mapping that answers later cannot run on wasm at all, which is pinned separately.

### What no tool reports

A sanitizer only sees what the run reaches, and most of the defects found here were outside every tool.

- A data view that copies where it used to alias leaves a test asserting something that no longer holds, and the assertion fails inside a callback where nothing can hear it. Breaking the test on purpose is what finds it.
- The wasm heap grows into a new buffer and detaches every typed array taken from the old one. Nothing throws, the array simply reports length zero, so a stale read looks like an empty payload rather than an error.
- `AttachCurrentThread` without a matching detach is not a leak any sanitizer flags. It is a runtime abort when the thread ends, and only on a real Android runtime.
- A mapping that answers with a local buffer is a use after return that shows up only on the bridges reading the answer after the call has unwound, which is why the Python and wasm suites failed on what the C++ one accepted.
- A JS number is a double, so an integer past `Number.MAX_SAFE_INTEGER` is rounded on parse with no diagnostic at all. Only comparing against the original source text catches it.
- R8 renames a field the serializer reads by name, so a release build stops sending parameters while every debug build keeps working.

## Decisions that are settled

These read like gaps to anyone auditing the repository and are deliberate, so they are written down
rather than raised again.

There is no workflow that publishes anything. Nine workflows verify and none of them ships, because
this repository is a template someone clones rather than a product installed from a registry. The
artefacts are built and validated so a clone can produce them, and pushing them anywhere belongs to
whoever cloned it.

Every manifest declares `1.0.0` and stays there. Versioning is a release cut from a commit rather
than a number moved through the manifests, so the three places that name it are not a source of
drift to remove.

The flutter plugin points at the local build for ios and macos. Three of its five platforms build
from source through cmake and those two vendor an xcframework, which is what lets the sample run
against what was just built instead of against something published.

## Finding one defect means looking for it six times

The six bridges are written to the same design, so a defect in one is a hypothesis about the other
five rather than a local accident. This is not a preference, it is what the record shows. The key
taken and never dropped on a failed dispatch was found and closed on python and dart and sat
untouched on kotlin for as long as nobody looked. The empty response handed to a parser was fixed on
python and was pinned by no test on four of the others. The data view decoder that raises, the
function name that is not text, the encode that ends the process, the second initialize that applies
one field of the config it discards, the proxy that keeps its mappings after finalize: every one of
them was found on one bridge and every one of them had to be checked on the rest before it could be
called closed.

So a finding is not finished when the bridge it was found on is fixed. It is finished when the same
question has been asked of all six and the answer for each is either the same fix or a written
reason why that language cannot have it, which is usually that the language makes the failure
impossible rather than that the code happens to be right. A closing note that names one bridge and
says nothing about the other five is an unfinished finding.

## Audit checklist

This is the master list for the production audit. An item is only ticked when the change is
implemented, validated by something that would fail without it, and written down. An item that
cannot be validated says so and says why, because a guard nobody proved is worth what it was
proved to be worth.

Where an entry names a defect, the defect was found and closed. Where it names a check, the check
was run and the result is recorded whether or not it changed anything, since knowing an area is
clean is worth the same as knowing it is not.

### A. Memory, lifetime and ownership

- [x] **A1.** Buffers walked in strides stop at the last whole element, on both grayscale mappings,
  rather than reading `data[i + 3]` past the end.
- [x] **A2.** A mapping never trusts the dimensions the caller declared over the size of the buffer
  it received.
- [x] **A3.** A view decoded from a response carries no address, so every helper that reads one
  answers with nothing rather than reading from address zero.
- [x] **A4.** A mapping that answers with a view keeps the buffer alive after it returns, since the
  bridges read it once the call has unwound.
- [x] **A5.** A view is released only by the side that allocated it, on all six ownership models.
- [x] **A6.** No language takes the address of a garbage collected array.
- [x] **A7.** The owned buffers the c layer hands the host carry exactly what the size says, with
  no terminator the documentation denies, and asking for zero bytes still answers a valid pointer.
- [x] **A8.** The awaitable never resumes inside `await_suspend`, since that destroys the frame the
  function is about to return to.
- [x] **A9.** The ios sample stops its capture session when the view goes away.

### B. Concurrency and shared state

- [x] **B1.** Every keyed registry takes an entry rather than reading then removing it, so a
  response can only ever resolve once.
- [x] **B2.** Iterating a shared container while calling out to user code runs over a snapshot.
- [x] **B3.** The unique id counter is atomic where the language has threads, counts from one on
  all six, and reaching its end is defined rather than silent, which typescript was not, since
  a double stops advancing and repeats one key for good instead of wrapping.
- [x] **B4.** Every jni reference a mapping can reach from any thread is atomic, which is the class,
  the three call entry points, the java vm, the class loader and its method id. The two ids only
  the lifecycle reads are plain and published through the class, which is stored after them and
  taken before them, so the pair is a release and an acquire rather than an unsynchronized read.
- [x] **B5.** The c abi function pointers are atomic, written at initialize and read from any
  thread that answers.
- [x] **B6.** A cancelled call drops its registration, on the two bridges where a waiting caller
  can be abandoned.
- [x] **B8.** The dart bridge belongs to one isolate, which is what its synchronous answer costs,
  and the guide says so rather than leaving a second isolate to end the process. Its own suite
  no longer runs files concurrently, which is what had been hiding it from `dart test`.
- [x] **B7.** The thread sanitizer was shown to reach the races the stress suites are credited
  with, by removing the locks from `TSMap` and the atomic from `UniqueID` and watching it report.
- [x] **B9.** The swift singletons say in the type system what their locks already do, so the
  library carries no warning under complete concurrency checking and compiles in the language mode
  where those warnings are errors.

## Code standards

These apply to the library, the bridges, the samples, the suites and the build files, in every language. Three things are outside them and each for its own reason: the task runner under `core/` and `xplpc.py` is not shipped code and keeps its own conventions, `cmake/ios/ios.toolchain.cmake` is vendored under a licence whose header and documentation are not ours to rewrite, and the flutter example's linux, windows, macos, ios and android directories are what `flutter create` writes, which is the only thing that keeps them from rotting again. Each language has a format task and each one reads its own configuration, which is `.clang-format`, `.editorconfig`, `.swiftformat`, `black`, prettier and remark. Three of those run in a job that fails on any diff, since black, prettier and remark are the ones whose version is pinned, and the other four come from the system or from brew and would go red on an image bump rather than on a mistake. `swift-lint`, `kotlin-lint` and `python-lint` run the three linters that read `.swiftlint.yml`, `detekt.yml` and `ruff.toml`, and every job runs the one for its language.

**Comments.** Rare and only where the code cannot explain itself. Every comment is a complete sentence, starts with a capital letter and ends with a full stop, and a second sentence starts on its own line rather than continuing the first. A sentence is never split across lines and never continues on the next one. When a sentence would have to begin with an identifier spelled in lowercase, the identifier keeps its exact spelling and the sentence is rewritten so it does not sit at the start. A comment above a function, method, class or module says what it does for whoever calls it and never how it is implemented inside, which is why the comments here sit next to the code they explain instead. No decorative separators, no section banners, no restating what the next line does, and nothing verbose, fragmented or narrative. A semicolon never splits one sentence into two, which applies to this file as much as to the code. Code and comments are in English.

A section banner is the shape this rule is broken in most often, and a build file is where it hides, since `# tests` above `if(XPLPC_BUILD_TESTS)` reads like structure rather than like a comment. Forty seven of them sat across the root `CMakeLists.txt`, thirteen per target lists and the three dependency files, each naming what the next line already said.

**Structure.** A function has a visible beginning, middle and end. Separate blocks of different responsibility with one blank line, and never stack conditionals, loops, state changes and returns into one visual block. Prefer early returns, never write `else` after `return`, and avoid nesting that an early return removes. Extract a function when one accumulates responsibilities, not to make it shorter.

**No legacy.** No backward compatibility shims, no version checks for how something used to work, no generic fallbacks, no dead code. When behaviour changes, change every call site.

**Errors.** Failing paths log through the platform logger and answer the caller with the empty value for its type. Never leave a caller waiting, not even when the host itself is out of reach, which is why routing a call to a host that cannot be entered from the current thread still answers instead of returning. A proxy reached before the library was initialized answers the same way, since the native side holds the callbacks from the moment it loads and only the host knows whether it is ready. A proxy reached after it was finalized answers the same way too, because the call is routed by a `hasMapping` that was true a moment earlier and nothing else will ever resolve that key.

**Entry points.** The public surface is small and fixed: `XPLPC.initialize`, `MappingList.add`, `Client.call`, `Client.callSync` and `Client.callAsync`, `DataView`, and the `xplpc_*` C functions. C++ adds `CallAwaitable`, since `co_await` needs a type to name and it is what `callAsync` answers with. Internals are refactored freely, entry point signatures are not. The binary agrees with that list rather than merely documenting it, since the visibility presets are hidden and only `XPLPC_API` and `JNIEXPORT` publish anything, so a new entry point that is not marked is not reachable and a helper that is marked widens the surface. A helper added to a bridge is named the way that language spells internal, which is why the python client keeps `_dispatch` out of the way of `call` and its variants.

**Types.** A value read out of a `Message` is checked against the requested type and answered with null when it does not match, on the four bridges where reading one names a type, and the mismatch is reported through the logger like every other failing path. Only C++ reported it for a long time, so on Kotlin, Swift and Dart a mapping reading a value as the wrong type saw a null it could not tell from an absent one, which is the same defect the empty answer rule exists to prevent. All four pin it now with a mapping that reads one value two ways. Python names none, since `Message.get` answers whatever the wire carried and the caller decides, which is what reading a value looks like in that language. TypeScript names one and cannot use it, because its generics are erased and there is nothing left at runtime to compare against. An unchecked cast only moves the failure to a place with less context. Taking the check from the caller as a guard was tried and reverted: it makes every read of a value carry an argument, and the whole point of this bridge is that reading a value is direct. The cast stays, and so does knowing that a mismatch here surfaces where the value is used rather than where it is read.

**Initialization.** `initialize` assigns the config first, because a proxy may read it while registering, and flips the initialized flag last. A failure in between must never leave a singleton that reports itself as ready. The flag has to be its own state for that to hold: Swift derived `initialized` from the config being set, so it answered true from the moment the config landed and before the objective-c proxy was registered, and a call arriving in that window found no proxy and was answered empty by a library already claiming to be up. Nothing is registered before it: `MappingList.add` reaches the native side on the bridges that declare their names, so calling it first fails rather than silently registering into a bridge that is not there.

C++ had the same defect Swift had and nobody looked, because there the flag is not set by an `initialize` a consumer calls but by `NativePlatformProxy::initialize`, which ran it before `initializePlatform` rather than after. So the library reported itself ready before the consumer's mappings existed and before the proxy was in the list, and the same call sits under the c abi, jni and the wasm bindings, which each brought a native proxy up before registering the host one. `XPLPC::initialize` is the last step on all four now, and on c++ it is what a consumer calls rather than something a proxy does on their behalf, which is what makes the entry point list true there. What made this reachable rather than cosmetic is that `Client::dispatch` reads that flag, so the window answered a host owned name with a function not found instead of refusing.

**What a log may carry.** A failing path says what failed and where, and never what it was reading. The text a parser produces is not safe to report, since it echoes the input it choked on: nlohmann answers `last read: '"hunter2"}]} B'` and dart prints the whole document with a caret under the offending column, so a request carrying a password puts that password in a device log through a line that always reports. Every failing path therefore reports the failure through `Log.e` and carries the detail on a following `Log.d`, which is compiled out or switched off in a release build. That split is the reason the two levels exist, rather than a matter of how much anyone wants to read.

**Debug logging.** Each runtime decides for itself whether `Log.d` reaches anything, because there is no shared mechanism. Five of the six decide it at runtime, since a consumer holds a prebuilt artifact and a field problem is not a reason to rebuild the library. TypeScript is the exception and is right to be, because there the consumer compiles the source into their own bundle, so `import.meta.env.DEV` is their build rather than ours. C++ reads `XPLPC_LOG_LEVEL` and reports the value when it does not name a level, Swift writes to an `os_log` subsystem the system raises with `log config`, TypeScript keeps it for a development build only, Kotlin gates it on `Log.isEnabled`, which the android initializer sets from the application's own debuggable flag and the desktop one from `XPLPC_LOG_LEVEL`, and Dart and Python leave the decision to the level their logging framework is configured with. `Log.e` always reports.

What each level may carry follows from that. An error names what failed and where, which is a function name, a parameter name, a class name or the entry point it happened in, and never the request, the response or the exception. A debug line carries the reason, which is where the exception text goes, because a parser quotes what it failed on: nlohmann appends the bytes it last read and a dart `FormatException` prints the whole document. So the same failing path writes twice, an error a release build keeps and a debug line only a development build reaches, and neither one leaves the failure unreported.

Every bridge writes through its own `Log`, and it has to be a named one, so a consumer can filter or silence this library without touching its own logging. Python had no `Log` at all and called the root logger directly from three files, which is the one sink an application cannot separate itself from, and the kotlin desktop logger reached `Logger.getGlobal()` while the android one already tagged with `Constants.LOG_GROUP`. Both name `XPLPC` now, the same as Dart.

**Answering without an event loop.** `call` takes a callback and needs no loop, which is what serves a caller that has none. Python has the same two entry points as every other bridge for that reason, and no pool of its own.

**Single threaded runtimes.** Dart isolates and JavaScript have no preemption between synchronous statements, so registries there are plain synchronous maps. A lock adds nothing and turns registration into a microtask, which loses the answer when the native side replies in the same tick.

The wasm module is linked without pthreads, so this goes further there than it does for the registries: a mapping that starts a thread cannot run at all, and `std::thread` fails at construction. What matters is that it fails the way everything else does, reporting through the logger and answering the caller with the empty value, so a mapping written for the other bridges degrades here instead of hanging or taking the module down. The suite pins that, since it is the only bridge where a `sample.async` shaped mapping never answers with anything.

**What a call promises.** `call` hands the request over and answers through a callback. `callAsync` hands it over and answers through the waiting form of the language, and it always gives control back to the caller's scheduler before the answer arrives. `callSync` hands it over and answers with the value itself, and only when the mapping had already answered by the time the dispatch returned. Those three sentences are the whole contract and they read the same on every bridge but one. TypeScript has a single `call` that answers with a promise, since a promise is both shapes at once and can be handed a callback with `then`, so a second entry point there would name something the first already is.

`callSync` never waits, which is what makes it expressible on all six rather than on the five where a thread can be blocked. Dart and TypeScript have one thread apiece and no way to give it up and get it back, so a blocking read there is a deadlock with no diagnostic rather than a slow call, and the same shape written as a read of an answer that is already there costs those two nothing. What it reads is decided by the mapping and not by the call site: an answer produced before the dispatch returned is there, and anything else is not, whichever thread produced it and whatever language the mapping is written in.

The failing path is the ordinary one. The key is taken back, so a mapping that answers later resolves nothing and leaves nothing registered, and the caller is told through the log rather than through the value, since the empty value is also what a mapping with nothing to answer produces. That the two are indistinguishable at the call site is the cost of the entry point and is written in every guide rather than left to be discovered.

One bridge cannot reach its own mappings this way and it is not a gap in the code. A TypeScript mapping answers with a promise, which resolves in a microtask and therefore never inside the call, so `callSync` there reaches the mappings the wasm module owns and answers empty for every mapping the page owns. The suite pins that rather than leaving it as a surprise.

The library creates no thread, anywhere. Where the work runs is decided by the mapping and by nothing else, which is why the one rule a mapping has to follow is to never hold the bridge: it starts its work, leaves it running and returns, as `sample.async` does. A mapping that blocks instead blocks whoever called it, and that is a mapping written against this documentation rather than something the library detects or compensates for.

Where the suspension comes from differs, and only one bridge needs to be told. Kotlin runs straight through `suspendCancellableCoroutine` when the continuation is resumed inside the block, so `callAsync` yields before dispatching and a test goes red when that yield is taken away. The other four get it from their own machinery: an `async` function in Dart returns a future that completes a microtask later, awaiting an answer in Python goes through `call_soon_threadsafe` so the future is never already done, calling a nonisolated async function from an isolated context in Swift crosses an executor boundary, and a resolved promise in TypeScript queues a microtask. Each of those was measured by taking the mechanism away and watching whether anything noticed, which is how three yields that looked necessary turned out to be redundant.

C++ has no scheduler to give a turn to, so `callAsync` there is an awaitable that suspends whenever the answer is not already there and resumes on the thread that produced it. An answer that arrives while the coroutine is still suspending is taken by the return value of `await_suspend` rather than by resuming, since resuming there would destroy the frame that function is about to return to, and an inline mapping makes that the ordinary case rather than a rare one.

What this means for a caller is that `call` returns before the answer whenever the mapping needs time, and the callback then runs on the thread that produced the answer, not on the thread that made the call. A C++ caller reaching an Android or Apple mapping that performs a network request gets its callback on a JVM worker or on the queue the mapping answered from, so anything the callback touches has to be safe there, and it has to capture owned copies since the calling frame is long gone.


This holds in both directions, and only one of them was ever proven. A mapping the core owns answering late is what `sample.async` and the c suite's `test.detached` cover. A mapping the *host* owns answering late is the http case, where the host cannot answer until a round trip completes, and no suite had it. Each bridge defers the way that language does: a thread on Kotlin and Python, `asyncAfter` on Swift, a later event loop turn on Dart, a resolved promise on TypeScript, and a detached thread calling `xplpc_native_call_proxy_callback` on the c abi. Each of those tests asserts the answer had not arrived when the call returned, since a mapping that holds the bridge would pass a test that only checks the value.

Writing that down found two bridges where it could not work at all. Swift declared the responder non escaping, which is the default for a closure parameter, so a Swift mapping could not store it and answer later and the compiler said so the moment one tried. And Dart wrote `"p": null` for a request with no parameters where the format says an array, then failed to iterate it on the way back in, so every no argument host mapping was unreachable there behind a single log line. Python could not read that shape either, while C++, Kotlin, Swift and TypeScript all read a missing parameter array as no parameters, which is what the reference does.

**Answering from another thread.** Which channel an answer travels through is decided by the thread it is produced on, never by who made the call.

Only the C ABI has a second channel, and only Dart and Python register it, because they are the two hosts reached through that ABI. JNI, Objective-C and WASM have nothing of the kind and need nothing: a native thread attaches to the JVM through `ScopedThreadAttachment`, an Objective-C object takes a message on any thread, and the WASM module only ever has the one thread JavaScript gave it.

The C layer needs it for two different reasons that happen to share a channel. Dart cannot be entered at all from a thread the isolate does not own, so a `Pointer.fromFunction` callback invoked from a foreign thread aborts the process, and the answer has to be handed to a `NativeCallable.listener` that queues it onto the isolate's event loop. Python can be entered from any thread, and only needs the buffers to outlive the native frame that is already gone. Both are served by `FuncPtrToOnNativeProxyCallbackFromThread`, whose buffers the host owns and releases with `xplpc_free`.

`HostCallScope` is what tells the two apart. It marks a thread for as long as it is running a call the host started, so an answer produced there is delivered directly and copies nothing, which is what keeps `Client.call` answering before it returns. An answer produced anywhere else takes the owned channel. Both callbacks are optional: a host that never answers off its own thread passes null, and a call that would need the missing channel is answered with the empty value rather than left waiting. What that leaves an implementer to decide is documented in the c guide rather than only here, since the four pointers are two pairs of the same event and the suffix says only which thread it arrived on, and the two situations that reach a `FromThread` one are a mapping that took its time and a host mapping reached from a thread the host did not start.

A call made from a user interface with a network request on the other side is the shape that puts all of this together, and nothing in it blocks the interface:

```
ui thread          Client.call hands the request over and returns immediately
native             the mapping starts the request, leaves it running and returns
ui thread          free, the whole crossing took microseconds
network            the request completes, later, on a thread of its own
that thread        the mapping calls r(value)
c layer            HostCallScope is not active here, so the owned channel is used
isolate            the listener queues the answer onto the event loop
ui thread          the callback runs and the interface updates
```

Reverse the direction and the same rules give a different route. When the mapping doing the request belongs to the host, the call reaches it on the host thread and it returns immediately with the request in flight, and the answer it produces later is already on a thread the host owns, so it goes back through the direct entry point and the second channel is never used. This is why the channel exists at all and why it is not a thing every bridge implements.

For the same reason the c layer is never asked, from native code, whether the host owns a function. The host declares its names with `xplpc_native_add_mapping` as it registers them, and `hasMapping` is resolved from that set, so routing a call never has to reach a runtime that may be unreachable from the current thread. Only that layer needs it, which is why only `MappingList.add` on dart and python reaches the native side. The jni, objective-c and wasm proxies still ask their host directly, since a jni environment can be attached to any thread, an objective-c object can be messaged from any thread, and the wasm module only ever runs on the one thread javascript gave it. The first two answer false rather than raising when the bridge is not there to ask.

### C++

- C++20, four space indent, Allman braces, `#pragma once` in headers. The standard is what it is for the coroutine `callAsync` answers with, which is also why the matrix carries no compiler older than that.
- Namespaces are `xplpc::<area>`, closed with `} // namespace <name>`.
- No anonymous namespaces. Something either belongs to a class, or it belongs to a helper class, one class per file.
- Prefer `const`, references and smart pointers. No raw owning pointers, no C casts, no macros where a constant or template works.
- Headers declare, they do not document. No comments describing members or sections.
- Shared state is guarded. `TSMap` for keyed collections, `std::shared_mutex` for lists, `std::atomic` for flags and function pointers, `std::call_once` for singletons and one time registration.
- Iterating a shared container while calling out to user code is done over a snapshot taken under the lock, so a callback can reenter without deadlocking.
- Lambdas do not format well, so wrap them in `// clang-format off` and `// clang-format on` and hand format the body.
- Callbacks that outlive the current frame capture owned copies, never references or borrowed pointers.

### C interface

- Public headers are valid C. Types come from `<stdbool.h>` and `<stddef.h>`, and the declarations sit inside an `extern "C"` block guarded by `__cplusplus`.
- Exported symbols are `xplpc_*` and marked with `XPLPC_API`.
- Buffers arrive as pointer plus size, always. Copy them before the call can outlive the frame, and never rely on null termination.
- The host declares the names it owns with `xplpc_native_add_mapping` and drops them with `xplpc_native_clear_mappings`, so `hasMapping` never has to call back into a runtime the current thread cannot enter.
- A callback whose name ends in `FromThread` owns the buffers it receives and releases them with `xplpc_free`. Every other callback borrows them for the length of the call.

### JNI

- Local references are wrapped in `ScopedLocalRef`, never left for the frame to reclaim.
- Classes and method ids are resolved once during initialization and kept as global references, released in `finalizePlatform` after the Java side has been notified.
- Strings cross through `JNISupport`, which converts UTF-16 to real UTF-8 rather than the modified UTF-8 that `GetStringUTFChars` returns.
- Every call into Java is followed by an exception check that reports and clears. A pending exception makes the next JNI call undefined.
- The address of a `jbyteArray` is never taken. `GetPrimitiveArrayCritical` stops being valid the moment it is released, so a direct `ByteBuffer` is used whenever native code needs a stable address.
- Callbacks that escape a JNI entry point convert every `jstring` to `std::string` first.

### Objective-C++

- Bridge classes live in `.mm` files and expose C++ types only through the `xplpc::proxy` namespace.
- Blocks and lambdas capture the receiver weakly, then promote it, so a late callback is a no-op instead of a dangling access.
- Never name a class method `initialize`, it collides with the runtime hook.
- The two headers the framework ships are guarded with `#ifndef`, since anything including them may be plain C. Everything else here is internal and uses `#pragma once` like the rest of the project.

### Swift

- Types are `public` only when the sample or the tests need them, and a type carrying no public member publishes a name and nothing reachable, which is what `UniqueID` did while this file said it was internal.
- Shared state is guarded by `NSLock` with `defer { unlock() }`, never by a semaphore, and the lock is released on every path including the miss path.
- Pointers into Swift storage are only valid inside the closure that produced them, so any API handing one out is scoped, like `DataView.withByteArray`.
- Continuations are resumed at most once, guarded by a local flag.
- `Log` writes to an `os_log` subsystem named `XPLPC`, so a consumer filters or silences this library on its own and raises it to debug with `sudo log config --subsystem XPLPC --mode "level:debug"`. `Log.e` always logs.

### Kotlin

- The library lives in `kotlin/shared/src` and is compiled by both the Android and the desktop Gradle projects, so it must not depend on the Android SDK.
- Shared collections are `ConcurrentHashMap`. Take and invoke in one step with `remove(key)?.invoke(...)`.
- Gson is built once and reused, it is immutable and thread safe after `create()`.
- Coroutine continuations check `isActive` before resuming and unregister their callback in `invokeOnCancellation`.
- Serialization is reflective by design, since any consumer type must cross the bridge without annotations or a generator. That makes `consumer-rules.pro` part of the contract: anything reached by name at runtime has to be kept there. Two groups qualify, the classes JNI resolves by name, and the fields the serializer reads to build the wire format. Adding a field to `Param` or a DTO to `JsonSerializer` without a matching keep rule breaks release builds only, where R8 renames it and the native side stops seeing the parameters. The Android sample builds its release variant with `minifyEnabled true` so the rules are exercised on every run.

### Dart

- An isolate is single threaded, so registries are plain synchronous maps. Never make registration async, the native side can answer before the future completes.
- An ffi signature declares the width the C side actually uses. A `size_t` described as `ffi.Int32` still passes on arm64, because the value happens to fit the low half of the register, and it stays wrong everywhere that is not true.
- A callback reached from a thread the isolate does not own has to be a `NativeCallable.listener`, and its `keepIsolateAlive` is false so a test process can still exit.
- Every `toNativeUtf8` has a matching `malloc.free`, done in a `finally`. Allocation and release live in `PlatformProxy`, not in callers.
- Native memory owned by a Dart object is released through an explicit `dispose`, and the factory that allocates it says so.
- Reflectable output is generated, run `dart run build_runner build` after changing a reflected type.

### TypeScript and WASM

- The sample is a Vue 3 application built by Vite, linted by ESLint flat config in `eslint.config.js` and formatted by Prettier through `prettier/prettier`.
- TypeScript stays on 6 until the tools around it catch up. TypeScript 7 is the native compiler and dropped the javascript entry points both of them reach into: `vue-tsc` dies resolving `typescript/lib/tsc`, and `typescript-eslint` refuses outright and tracks support for 7.1. Running one version for the type checker and another for the linter is not a trade worth making.
- No `@ts-ignore` and no unsafe `as`. The Emscripten surface is declared in `WasmModule`, including the runtime exports enabled by `EXPORTED_FUNCTIONS` and `EXPORTED_RUNTIME_METHODS`. Where the runtime offers something the standard library does not describe yet, such as the original text a reviver receives, it is declared rather than cast away. What remains is the decode of an answer, which cannot be checked without an argument `Client.call` is not allowed to grow.
- The classes carry the same names as every other bridge and nothing is prefixed to keep it away from a global. A module scopes what it imports, so `Request` and `DataView` shadow the globals of those names inside the files that ask for them, and a file that needs both renames one at the import.
- Values coming from the DOM are narrowed with `instanceof`, never cast. A template ref that is not mounted yet returns null and the caller returns early.
- Heap memory allocated through `DataView` is owned by the returned view and released with `DataView.free`.
- The heap grows into a new buffer, which detaches every typed array taken from the old one, so the bytes are never handed out. `DataView.withUint8Array` and `withUint8ClampedArray` build the array from the current buffer and pass it to the body, where it cannot outlive the read.
- `CallbackList` and `UniqueID` are synchronous. The wasm module answers inside the same tick, so an awaited registration would be queued after the answer.
- A generic read returns `T | undefined`. Widening it to `unknown` makes the type parameter meaningless for every caller, and the type parameter cannot be verified at runtime either, so a caller reading a value the wire did not carry gets what the wire did carry rather than nothing. Every other bridge answers null there.
- Deprecation warnings are only silenced for third party stylesheets, never for project code.

### Python

- Package layout is `src/xplpc/<area>/<module>.py`, built from `pyproject.toml`.
- Buffers cross to C as `POINTER(c_char)` with an explicit length. `c_char_p` would stop at the first null byte and silently truncate the payload.
- The ctypes callback objects are stored on the proxy. Letting them be collected leaves the native side holding a dangling function pointer.
- Singletons guard construction with a class level lock and their data with a separate instance lock, so one can never block the other.
- Buffers crossing to C are encoded once and passed with an explicit length.
